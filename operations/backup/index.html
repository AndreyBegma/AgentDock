Backup and restore

A backup is two things taken together: the PostgreSQL database and the data volume.

  • The database holds everything you see in Nautelle: projects, cards, sessions, usage, the audit log, and the stored secrets in sealed form.
  • The data volume (/data in the API container) holds secrets.json, the keys the API generated on its first start (APP_ENCRYPTION_KEY, AUDIT_HMAC_KEY, LLM_SECRETS_KEY), and the board card attachments.

secrets.json is as important as the database: without it, a restored database cannot unseal its secrets (two-factor sign-in, the Telegram bot token, AI provider keys, GitHub App and webhook secrets) and the audit chain no longer verifies. Keep nautelle/.env too, for the database and Redis passwords, and nautelle/api.env if you have one.

Back up

Section titled “Back up”

Store data.tar apart from the dump, and as safely: whoever holds both can read every stored secret. Either alone is useless to them, and to you.

Redis holds only job queues and is not part of the backup; a restored install starts with empty queues, and schedules are recreated from the database.

Volume-level backups

Section titled “Volume-level backups”

The volumes are nautelle_pgdata, nautelle_data, nautelle_redis and, in domain mode, nautelle_caddy-data. Back them up with your own tooling while the stack is stopped (docker compose stop); a copy of pgdata taken while PostgreSQL runs is not consistent.

Runners

Section titled “Runners”

A runner keeps its own state on its machine: its token and policy in ~/.config/nautelle/runner.json, and the event spool. Nothing there needs a backup — a lost runner is paired again — but the worktrees of running cards live in your repositories on that machine.
