# C-366: Zero-config API: generate its secret keys on first boot

## Why
A self-hosted install should need no hand-made secrets (part of the one-command install, see the "Install in one command" card). Today `APP_ENCRYPTION_KEY` must be generated by hand (staging's `refresh.sh` does it), and `AUDIT_HMAC_KEY` / `LLM_SECRETS_KEY` are optional with a warning — so most installs run without them.

## What
- At boot, for each of `APP_ENCRYPTION_KEY`, `AUDIT_HMAC_KEY`, `LLM_SECRETS_KEY`: if the env var is set, use it (unchanged behaviour). If not, read it from `${NAUTELLE_DATA_DIR:-/data}/secrets.json`; if that file has none, generate 32 random bytes (base64, same format the code already expects), write the file with mode 0600 atomically, log once that the key was generated and where it lives (never the value).
- One place does this before any module reads the keys (config bootstrap), so every consumer keeps reading config as today.
- Refuse to start when the data dir is not writable and a key is missing — no silent in-memory key (data encrypted with it would be lost on restart).
- In the Dockerfile, declare `/data` (attachments already live in `/data/attachments`). Document `NAUTELLE_DATA_DIR` in `apps/api/.env.example`; note in the docs that backing up the `/data` volume is required, the key file is as important as the database.
- Dev (`apps/api/.env`) keeps working without changes.

## Tests
Unit tests: env wins over file; file reused across boots; generated key has the right length/format; unwritable dir + missing key → start refused; existing file is never overwritten.
