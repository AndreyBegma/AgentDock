# C-365: Install in one command: published images and a single compose file (localhost, Cloudflare tunnel, own domain)

## Why
Installing Nautelle today means cloning the repo, building `api`/`web` images from source on the host (no registry — `deploy/staging/build-staging.sh`), copying a staging-specific compose with Cloudflare baked in, filling `POSTGRES_PASSWORD`, `REDIS_PASSWORD`, `env/api.env` (API_URL, WEB_URL, APP_URL, PUBLIC_URL, TRUST_PROXY, keys…), then `bun run admin:create` inside the container. Woodpecker (https://woodpecker-ci.org/docs/administration/general) is the bar: pull a published image, one short compose file, a handful of env vars, open the browser, it works.

## What
1. **Published images.** On a release tag (`vX.Y.Z`) a trusted Woodpecker pipeline builds and pushes `ghcr.io/andreybegma/nautelle-api:<version>` + `:latest` and the same for `nautelle-web` (multi-arch amd64/arm64 if the builder allows; amd64 is enough for the first cut). Images stay pinned by digest at their base; PR pipelines never get the push secret (ADR-0053).
2. **`deploy/compose/`** — the public install: `docker-compose.yml` + `.env.example`, using the published images, postgres, redis and a Caddy proxy (`/api/*` → api, `/*` → web). One required setting: `NAUTELLE_URL` (default `http://localhost:8000`). Three exposure modes, chosen by compose profiles, no file edits:
   - **localhost** (default): Caddy on `127.0.0.1:${NAUTELLE_PORT:-8000}`, plain HTTP.
   - **Cloudflare tunnel**: `--profile tunnel` adds `cloudflared` with `TUNNEL_TOKEN`; Caddy is not published on the host.
   - **own domain**: `--profile tls` — Caddy gets `NAUTELLE_DOMAIN`, publishes 80/443 and does automatic HTTPS.
   Postgres/Redis passwords default to values generated by the install script (below) — never a hard-coded default in the file.
3. **`deploy/compose/install.sh`** (curl-able): checks docker + compose v2, downloads the two files into `./nautelle`, generates `.env` with random passwords, asks/accepts `--url`, `--tunnel-token`, `--domain` flags, runs `docker compose up -d`, waits for the API health check and prints the URL plus the first-run setup link. Re-running it is safe (keeps an existing `.env`).
4. Derive `API_URL`, `WEB_URL`, `APP_URL`, `PUBLIC_URL` from `NAUTELLE_URL` in the compose file (each still overridable). `TRUST_PROXY=uniquelocal` set in the file.
5. **Docs:** `docs/guides/install.md` (quick start = 3 commands, then the three modes, upgrade = `docker compose pull && up -d`, backup of the volumes, pairing a runner), link from `README.md`; staging keeps its own setup. **ADR** "Nautelle installs from published images with one compose file" (take the next number from origin/develop).

## Out of scope (separate cards)
Generating the encryption/audit keys on first boot, and the first-run admin page in the web app. This card's compose must work with them; until they land, `install.sh` generates the keys into `.env` and prints the `admin:create` command.

## Done when
On a clean machine with only Docker: `curl -fsSL …/install.sh | sh` → open `http://localhost:8000` → Nautelle answers within ~1 minute (image pull excluded). Same with `--tunnel-token` and with `--domain`. `bun run check` green; `scripts/check-ci.ts` still passes with the new release step.
